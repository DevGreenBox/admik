## Принципы, обязательные для каждой задачи

Эти правила вытекают из `CLAUDE.md`, ADR-004 и `docs/02-модель-развёртывания.md` и
**применяются ко всем задачам-разработки во всех этапах**. В декомпозиции ниже они не
повторяются дословно у каждой задачи — но обязательны:

1. **Сначала тесты, потом код (ADR-004).** Для каждой задачи-разработки сперва пишутся
   тесты (Vitest — логика/валидация, Playwright — e2e/a11y админки), которые **падают**
   на отсутствующей реализации, затем пишется код до зелёных тестов. QA проверяет
   покрытие до приёмки. В декомпозиции это отражено отдельным первым пунктом «Тесты».
2. **Идемпотентные миграции.** Любая новая таблица/изменение схемы — миграцией с
   `CREATE ... IF NOT EXISTS` (и безопасными `ALTER`), повторный накат не ломает данные.
   Накат на пустую БД — одной командой.
3. **Флаги модулей.** Любой функционал, относящийся к модулю, уважает флаг включения из
   `lib/config/modules.ts` (переменная окружения `ADMIK_MODULES`, значения:
   `catalog`, `orders`, `cdek`, `cms`). Выключенный модуль не отдаёт UI/API/cron.
4. **Секреты — только в env.** Любой ключ/пароль/токен читается из переменной окружения
   через `lib/config/env.ts` (Zod-валидация). В репозитории — только `.env.example`.
5. **Mock-режим интеграций.** Любая зависимость от внешнего сервиса (СДЭК, платежи, S3,
   email) имеет mock/demo-режим, чтобы магазин без боевых ключей поднимался и проходил
   smoke-тест.
6. **Никаких хардкодов магазина.** Название, логотип, контакты, юрлицо, цвета, реквизиты,
   ключи — только в `.env`/таблице настроек, не в коде. Код единый и неизменный при
   подключении нового магазина (ADR-003, `docs/02`).
7. **Обратная совместимость.** Обновление кода существующего магазина не ломает его данные.

## Этап 1. Ядро + Auth + RBAC + каркас админки + audit_log — ⬜ todo

**Цель этапа.** Дать платформе фундамент прикладной логики: подключение к БД, миграции,
аутентификацию (сессии в БД), ролевую модель (RBAC), общий каркас админ-панели и сквозной
аудит действий. Без этого этапа невозможны модули 2–5.

### 1.1. Слой доступа к БД и движок миграций — ⬜ todo
- **Тесты:** проверка идемпотентности миграций (двойной накат), наличие двух ролей БД
  (app/migrator), защита от SQL-инъекций через tagged templates.
- **Что входит:** подключение `postgres.js`, runner идемпотентных миграций, разделение
  ролей `app`/`migrator` (паттерн 2x2, ADR-002).
- **Критерии приёмки:** миграции накатываются одной командой на пустую БД и повторно
  безопасны; запросы параметризованы; покрыто тестами.

### 1.2. Аутентификация (Lucia-подход, сессии в БД) — ⬜ todo
- **Тесты:** логин/логаут, срок жизни сессии, защита от timing-attack при проверке
  пароля, ротация сессии.
- **Что входит:** таблицы `users`/`sessions`, хеширование паролей, выдача/проверка
  сессий, middleware-гвард.
- **Критерии приёмки:** вход/выход работают; невалидные креды отклоняются с защитой от
  timing-атак; сессии хранятся в БД; покрыто тестами.

### 1.3. RBAC (роли и права) — ⬜ todo
- **Тесты:** матрица «роль → разрешение», запрет действий без права, проверка на уровне
  Server Action/API.
- **Что входит:** модель ролей и прав (источник — 2x2), гвард-функции для Server Actions,
  seed базовых ролей (владелец/администратор/менеджер и т.п.).
- **Критерии приёмки:** действие без нужного права блокируется на сервере (не только в
  UI); роли конфигурируемы; покрыто тестами.

### 1.4. Каркас админ-панели (layout, навигация, меню по модулям) — ⬜ todo
- **Тесты (Playwright):** доступность (a11y), отрисовка навигации, скрытие пунктов меню по
  выключенным модулям и по правам пользователя.
- **Что входит:** общий layout `/admin`, навигация, единый UI-каркас; меню строится по
  `getEnabledModules()` и правам.
- **Критерии приёмки:** каркас единый и брендируемый через конфиг; выключенный модуль не
  показывает свой раздел; проходит a11y-проверки.

### 1.5. Сквозной аудит (`audit_log`) — ⬜ todo
- **Тесты:** запись аудита при ключевых действиях, неизменяемость записей, корректные
  метаданные (кто/что/когда).
- **Что входит:** таблица `audit_log` (паттерн 2x2), хелпер записи, встраивание в
  унифицированный паттерн Server Action (гвард → Zod → БД → инвалидация кеша → аудит).
- **Критерии приёмки:** значимые действия фиксируются; журнал просматривается в админке;
  покрыто тестами.

### 1.6. Унифицированный паттерн Server Action — ⬜ todo
- **Тесты:** прохождение пайплайна гвард → Zod-валидация → запись → инвалидация → аудит;
  идемпотентность форм.
- **Что входит:** общий хелпер/обёртка для Server Actions, единообразная обработка ошибок
  и валидации (ADR-002).
- **Критерии приёмки:** все последующие модули используют единый паттерн; покрыто тестами.

- **Что входит:** процесс оформления заказа, создание заказа из корзины.
- **Критерии приёмки:** заказ создаётся атомарно; повторная отправка не дублирует заказ;
  покрыто тестами.

### 3.4. Управление заказами в админке — ⬜ todo
- **Тесты (Playwright + Vitest):** список/фильтры заказов, смена статуса с проверкой прав,
  запись в аудит.
- **Что входит:** раздел заказов в админке (TanStack Table), смена статусов, история.
- **Критерии приёмки:** менеджер управляет заказами по правам RBAC; действия в `audit_log`;
  тесты зелёные. (Точка интеграции со СДЭК — Этап 4.)

> **Зависимости:** Этап 2 (товары, остатки), Этап 1 (ядро).

## Этап 4. Интеграция СДЭК — ⬜ todo

**Цель этапа.** Модуль `cdek`: полноценная интеграция с API СДЭК, портированная из проекта
carre (ADR-002). Слоистая архитектура `Manager → Client → Services`. Уважает флаг `cdek`.
**Обязателен mock-режим** — магазин без боевых ключей СДЭК должен подниматься и проходить
smoke-тест.

### 4.1. Клиент СДЭК + OAuth-токен — ⬜ todo
- **Тесты:** получение/кеширование токена, обновление по истечении, **mock-клиент**.
- **Что входит:** HTTP-клиент API СДЭК, кеш OAuth-токена (паттерн carre), ключи — из env.
- **Критерии приёмки:** токен кешируется и обновляется; ключи только в `.env`; mock-режим
  работает; покрыто тестами.

### 4.2. Расчёт стоимости доставки (Calculator) — ⬜ todo
- **Тесты:** расчёт по тарифам, обработка ошибок, mock-ответы.
- **Что входит:** сервис расчёта стоимости/срока доставки.
- **Критерии приёмки:** корректный расчёт на реальном и mock-режиме; тесты зелёные.

### 4.3. ПВЗ (PvzService) — ⬜ todo
- **Тесты:** получение списка ПВЗ, фильтрация, mock-данные.
- **Что входит:** сервис получения пунктов выдачи заказов.
- **Критерии приёмки:** ПВЗ доступны в UI оформления/админке; mock-режим; тесты зелёные.

### 4.4. Создание и отслеживание отправлений (OrderService) — ⬜ todo
- **Тесты:** создание отправления из заказа, привязка к заказу (Этап 3), отслеживание.
- **Что входит:** создание отправлений СДЭК, связь с моделью заказа, статусы доставки.
- **Критерии приёмки:** отправление создаётся из заказа; статус отслеживается; покрыто
  тестами.

### 4.5. Webhook статусов (идемпотентность + IP-whitelist) — ⬜ todo
- **Тесты:** идемпотентность по UNIQUE-ключу (`cdek_status_log`), отбраковка чужих IP,
  повторные доставки webhook.
- **Что входит:** приём webhook СДЭК с идемпотентностью и IP-whitelist (паттерн carre),
  `StatusMap` для маппинга статусов.
- **Критерии приёмки:** дубли webhook не создают повторных эффектов; чужие IP отклоняются;
  покрыто тестами.

### 4.6. Печать документов (PrintService) — ⬜ todo
- **Тесты:** генерация/получение документов, обработка ошибок, mock.
- **Что входит:** получение печатных форм СДЭК (накладные и т.п.).
- **Критерии приёмки:** документы доступны менеджеру по правам; mock-режим; тесты зелёные.

### 4.7. Cron-воркеры и email-уведомления — ⬜ todo
- **Тесты:** воркеры `create-pending` / `notify-stuck`, отправка уведомлений (mock email).
- **Что входит:** фоновые воркеры (паттерн carre), email-уведомления по статусам.
- **Критерии приёмки:** воркеры идемпотентны; уведомления уходят в боевом режиме и
  мокаются без ключей; покрыто тестами.

> **Зависимости:** Этап 3 (заказы). Изоляция модуля: при выключенном `cdek` нет UI/API/cron.

## Этап 6. DevOps: copy-paste-деплой, бэкапы, мониторинг, обновления — ⬜ todo

**Цель этапа.** Довести модель развёртывания (`docs/02`) до продакшн-готовности: один
скрипт развёртывания, резервное копирование, мониторинг, логирование, обновления без
простоев. Это то, что делает подключение нового магазина процессом настройки, а не
разработки.

### 6.1. Скрипт развёртывания «из коробки» — ⬜ todo
- **Тесты:** прогон развёртывания на чистом окружении, проверка `/api/health` и smoke.
- **Что входит:** финализация `docker compose up -d` + `./scripts/init-shop.sh` как единого
  copy-paste-сценария (опирается на 0.11–0.12), параметры — из `.env`.
- **Критерии приёмки:** сторонний человек поднимает магазин по шагам `docs/02` (п. 1–7)
  без участия разработчика; smoke зелёный.

### 6.2. Резервное копирование (бэкапы БД и медиа) — ⬜ todo
- **Тесты:** создание бэкапа и проверка восстановления (restore-drill).
- **Что входит:** регламент и скрипты бэкапа PostgreSQL и S3/MinIO, расписание.
- **Критерии приёмки:** бэкап создаётся по расписанию; восстановление проверено; покрыто
  проверкой.

### 6.3. Мониторинг и логирование — ⬜ todo
- **Тесты/проверки:** срабатывание алертов на падение `/api/health`, сбор логов.
- **Что входит:** мониторинг доступности и ресурсов, централизованные логи, алерты.
- **Критерии приёмки:** падение сервиса детектируется; логи доступны для разбора.

### 6.4. Обновления без простоев — ⬜ todo
- **Тесты:** прогон обновления с обратной совместимостью миграций (без потери данных).
- **Что входит:** процедура обновления кода существующего магазина (rolling/zero-downtime
  насколько применимо к одному VPS), обратно-совместимые миграции.
- **Критерии приёмки:** обновление не ломает данные магазина (`docs/02`, чек-лист);
  откат предусмотрен.

### 6.5. Инструкция по развёртыванию для не-разработчика — ⬜ todo
- **Что входит:** `docs/09-инструкция-разворачивания.md` (анонсирована в `docs/02`, п. 7) —
  пошагово, языком не-разработчика: clone → `.env` → up → init → проверка.
- **Критерии приёмки:** по инструкции магазин поднимает человек без опыта разработки;
  каждый шаг проверяем.

> **Зависимости:** опирается на инфраструктуру Этапа 0 (0.11–0.13) и наличие рабочих
> модулей 1–5 для содержательного бэкапа/мониторинга.
